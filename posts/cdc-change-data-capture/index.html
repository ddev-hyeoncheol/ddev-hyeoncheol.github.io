📝 개요

데이터 엔지니어링의 관점에서, 일자 또는 시간 단위로 실행되는 전통적인 쿼리 기반 ETL/ELT 배치 처리 방식의 한계는 점점 명확해지고 있다. 특히, 실시간 대시보드나 사기 탐지(Fraud Detection), 시스템 간 데이터 동기화와 같이 실시간 데이터를 요구하는 사례가 증가하면서, 기존 배치 기반 방식으로는 이러한 요구사항을 근본적으로 충족하기 어려워졌다.

이러한 문제를 해결하기 위한 대안으로 CDC(Change Data Capture) 라는 개념이 등장했는데, 이번 포스트에서는 CDC 의 핵심 개념과 주요 구현 방식들을 살펴 보고, 스트리밍 기반 데이터 파이프라인에서 Log-based CDC 가 가지는 의미를 정리해 보고자 한다.

CDC(Change Data Capture) 란??

CDC(Change Data Capture) 는 데이터베이스에서 발생하는 데이터 변경 사항(Insert, Update, Delete) 을 거의 실시간에 가깝게 감지해, 이를 타겟 시스템(DW, 검색 엔진, 캐시 등) 으로 전달하는 매커니즘을 말한다. CDC 의 핵심은 단순한 데이터 복제가 아니라, 데이터베이스의 변경 이력을 하나의 이벤트 스트림으로 변환해 시스템 간 결합도를 낮추고, 데이터의 흐름을 비동기화하는 데 있다.

기존의 배치 기반 데이터 파이프라인은 쿼리를 통해 변경사항을 추적하거나, 주기적으로 전체 데이터를 다시 적재하는 스냅샷(Snapshot) 방식에 의존하는 경우가 많다. 이러한 접근 방식은 구현이 비교적 단순하다는 장점이 있지만, 변경 데이터의 누락 가능성, 높은 지연(Latency), 운영 DB 부하와 같은 구조적인 한계를 가지고 있다.

이에 따라 현대적인 아키텍처에서는 Kafka 와 같은 스트리밍 허브(Streaming Hub) 를 중심에 두어 소스 데이터베이스와 하위 시스템 간의 결합도를 낮추고, 이를 통해 다수의 타겟 시스템이 동일한 변경 이벤트를 각자의 처리 속도와 목적에 맞게 독립적으로 소비(Consume) 할 수 있는 구조를 설계한다.

CDC 의 구현 방식

CDC 는 구현 방식에 따라 크게 Query-based, Trigger-based, Log-based 의 세 가지로 구분할 수 있다.

Query-based 와 Trigger-based 방식은 변경 데이터를 추출한다는 기능적인 의미에서는 CDC 로 분류할 수 있지만, 데이터베이스와 하위 시스템 간의 결합도를 낮춘다는 CDC 의 핵심 가치를 온전히 충족하지는 못한다.

1. Query-based (쿼리 기반, Pull-based)

Query-based CDC 는 일정 주기마다 데이터베이스에 쿼리를 실행해 변경된 데이터를 조회하는 방식이다. 일반적으로 updated_at, version 등과 같이 시간에 따라 증가하거나 변경되는 컬럼을 기준으로 데이터 변경 여부를 판단하며, 배치 작업에 의해 주기적으로 실행된다. 데이터 변경을 외부에서 조회해 가져온다는 점에서 Pull-based 방식이라고도 한다.

Query-based 예시

SELECT *
FROM users
WHERE updated_at > '2024-03-08 00:00:00'
ORDER BY updated_at ASC;

장점

  • 낮은 구현 난이도 : 별도의 CDC 전용 도구나 데이터베이스 설정 없이, 기존에 사용하던 SQL 과 배치 인프라만으로도 구현이 가능하다.
  • 데이터베이스에 대한 낮은 종속성 : Binlog, WAL 과 같은 벤더 종속적인 내부 로그를 사용하지 않고 쿼리 결과에만 의존하기 때문에, 서로 다른 데이터베이스 환경에서도 동일한 패턴을 적용할 수 있다.
  • 단순한 운영 및 재처리 : 쿼리 단위로 변경 이력을 추적할 수 있어 디버깅이 비교적 쉽고, 특정 시점을 기준으로 쿼리를 재실행하는 방식으로 Backfill 처리가 가능하다.

단점

  • 정확한 변경 이력 추적의 한계 : 배치 주기 내 발생한 중간 변경 사항을 모두 추적할 수 없으며, DELETE 이벤트 감지가 불가능하다.
  • 구조적인 지연(Latency) : 배치 주기에 의존하기 때문에, 변경사항을 실시간으로 감지하지 못하고 구조적인 지연이 발생한다.
  • 운영 DB 부하 : 변경 데이터를 찾기 위한 반복적인 인덱스 스캔이 발생하며, 데이터 규모가 커질수록 운영 데이터베이스 성능에 직접적인 영향을 준다.

2. Trigger-based (트리거 기반, Push-based)

Trigger-based CDC 는 데이터베이스의 INSERT, UPDATE, DELETE 이벤트가 발생할 때마다 미리 정의된 트리거를 실행해 변경 사항을 기록하는 방식이다. 변경된 데이터는 별도의 변경 로그 테이블(Audit Table) 이나 외부 시스템에 저장되며, 변경이 발생하는 즉시 동작한다는 점에서 Push-based 방식이라고도 한다.

Trigger-based 예시

users 테이블의 email 컬럼 변경을 추적하는 MySQL 트리거 예시이다.

-- 1. 변경 이력 테이블 생성
CREATE TABLE users_audit_log (
    log_id INT AUTO_INCREMENT PRIMARY KEY,
    user_id INT,
    old_email VARCHAR(200),
    new_email VARCHAR(200),
    changed_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
-- 2. UPDATE 트리거 생성
CREATE TRIGGER after_users_update
AFTER UPDATE ON users
FOR EACH ROW
BEGIN
    IF NOT (OLD.email <=> NEW.email) THEN
        INSERT INTO users_audit_log (user_id, old_email, new_email)
        VALUES (OLD.id, OLD.email, NEW.email);
    END IF;
END;

장점

  • 변경 사항의 즉각적인 감지 : 데이터 변경 시점에 트리거가 실행되므로, 배치 주기에 의존하지 않고 변경 이벤트를 실시간에 가깝게 감지할 수 있다.
  • 직관적인 구현 구조 : 트리거와 로그 테이블만으로 변경 흐름을 구성할 수 있어, CDC 동작 방식을 이해하고 추적하기가 비교적 쉽다.
  • 추가 인프라 의존성 최소화 : Kafka, Debezium 과 같은 외부 CDC 도구 없이도 데이터베이스 내부 기능만으로 구현이 가능하다.

단점

  • 운영 DB 트랜잭션 경로에 대한 오버헤드 : 모든 DML(INSERT, UPDATE, DELETE) 에 대해 트리거가 실행되며, 이는 트랜잭션 경로에 직접적인 오버헤드를 추가해 운영 데이터베이스 성능에 영향을 줄 수 있다.
  • 확장성과 유지보수의 한계 : 테이블 별로 트리거를 관리해야 하고, 스키마 변경 시 트리거 수정이 필요해 운영 복잡도가 빠르게 증가한다.
  • 높은 벤더 및 스키마 종속성 : 트리거 문법과 실행 방식이 데이터베이스 벤더마다 상이하며, 특정 테이블 구조에 강하게 결합된다.
  • 복구 및 재처리의 어려움 : 트리거는 이벤트 발생 시점에만 동작하므로, 장애 발생 시 누락된 변경 사항을 소급해 재처리하기가 어렵다.

3. Log-based (로그 기반)

Log-based CDC 는 데이터베이스의 트랜잭션 로그(Binlog, WAL 등) 를 직접 읽어 데이터 변경 사항을 추출하는 방식이다. 데이터 변경이 커밋된 이후 트랜잭션 로그에 기록된 내용을 기반으로 이벤트를 생성하기 때문에, 운영 쿼리나 애플리케이션의 트랜잭션 경로에 직접 개입하지 않는다는 점이 가장 큰 특징이다. 일반적으로 Debezium 과 같은 CDC 커넥터를 사용해 변경 이벤트를 Kafka 와 같은 스트리밍 플랫폼으로 전달하는 구조가 널리 차용된다.

Log-based 예시

아래는 Debezium 커넥터가 MySQL 의 Binlog 를 읽어 Kafka 로 전송하는 CDC 메시지의 payload 를 추출해 단순화한 예시이다.

"payload": {
    "op": "c", // CREATE
    "before": null,
    "after": { "id": 1, "name": "Alice", "email": "alice@example.com", ... },
    "source": { "table": "users", "file": "mysql-bin.000003", "pos": 1216, ... }
}
"payload": {
    "op": "u", // UPDATE
    "before": { "id": 1, "name": "Alice", "email": "alice@example.com", ... },
    "after": { "id": 1, "name": "Alice", "email": "alice.new@example.com", ... },
    "source": { "table": "users", "file": "mysql-bin.000003", "pos": 2001, ... }
}
"payload": {
    "op": "d", // DELETE
    "before": { "id": 3, "name": "Charlie", "email": "charlie@example.com", ... },
    "after": null,
    "source": { "table": "users", "file": "mysql-bin.000003", "pos": 3409, ... }
}

장점

  • 정확한 변경 이력 추적 : 트랜잭션 로그에는 모든 INSERT, UPDATE, DELETE 이벤트가 커밋 순서대로 기록되므로, 중간 변경을 포함한 전체 변경 이력을 유실 없이 감지할 수 있다.
  • 운영 DB 트랜잭션 경로와의 분리 : 쿼리나 트리거를 추가하지 않고 데이터베이스 로그를 읽기 때문에, 트랜잭션 처리 경로에 영향을 주지 않는다.
  • 낮은 지연(Latency) : 로그가 생성되는 시점부터 거의 실시간으로 변경 이벤트를 소비할 수 있어, 실시간 대시보드나 시스템 간 데이터 동기화 요구에 적합하다.
  • 대규모 트래픽 환경에 대한 확장성 : 이벤트 스트림 기반으로 동작하며, Kafka 와 같은 스트리밍 플랫폼과 결합해 수평적인 확장이 가능하다.

단점

  • 높은 구현 및 운영 난이도 : 트랜잭션 로그 설정, 권한 관리, 오프셋 관리 등 추가적인 설정과 운영 복잡도가 발생한다.
  • 벤더 종속성 존재 : 데이터베이스 벤더별로 로그 형식과 설정 방식이 달라, 서로 다른 데이터베이스 환경에 따른 별도의 설정과 이해가 필요하다.

스트리밍 기반 데이터 파이프라인과 Log-based CDC

스트리밍 기반 파이프라인의 목적은 단순히 데이터의 변경을 빠르게 전달하는 데 그치지 않는다. 핵심은 데이터베이스의 상태 변화를 연속적인 이벤트 흐름으로 외부에 개방하는 아키텍처를 구축하는 데 있다. 이러한 구조는 데이터 엔지니어링 환경에서 다음과 같은 구조적인 이점을 제공한다.

1. Source DB 와 Consumer 간의 완전한 비동기 분리

스트리밍 기반 파이프라인에서는 소스 데이터베이스가 ‘누가, 언제, 어떻게 데이터를 소비(Consume) 하는지’ 를 알 필요가 없다. 모든 변경사항은 이벤트 스트림으로 발행되고, 각 하위 시스템(Downstream) 은 각자의 처리 속도와 목적에 맞게 이를 독립적으로 소비한다. 이로 인해 소스 데이터베이스는 트랜잭션 처리에만 집중할 수 있고, 소비자의 추가나 변경이 소스 데이터베이스의 구조나 성능에 영향을 주지 않는다.

Log-based CDC 는 애플리케이션 트랜잭션 경로에 개입하지 않고 트랜잭션 로그를 Non-intrusive 하게 읽어 이벤트를 생성하기 때문에, 소스 데이터베이스의 성능 저하나 스키마 수정 없이도 이러한 비동기 분리를 가장 자연스럽게 구현할 수 있다.

2. Event 단위 처리와 순서 보장

스트리밍 기반 파이프라인은 데이터 변경을 스냅샷이 아닌 이벤트 단위로 처리한다. 각 이벤트는 발생 시점과 순서에 대한 메타데이터를 포함하며, 이는 실시간 집계나 상태 기반 처리, 윈도우 연산과 같은 복잡한 스트리밍 처리의 전제조건이 된다.

Log-based CDC 는 커밋된 트랜잭션 로그를 기준으로 이벤트를 생성하므로, 중간 변경을 포함한 전체 변경 이력을 순서대로 유실 없이 유지할 수 있다. 이는 Query-based 나 Trigger-based 방식으로는 구조적으로 보장하기 어려운 특성이다.

3. 장애 복구와 재처리를 전제로 한 데이터 흐름

스트리밍 기반 파이프라인은 장애를 예외적인 상황이 아닌 필연적인 상황으로 간주하고 설계된다. 발행된 이벤트는 높은 내구성을 가진 로그 시스템(Kafka 등) 에 저장되며, 소비자는 오프셋을 기준으로 특정 시점부터 데이터를 다시 처리할 수 있다.

Log-based CDC 는 Kafka 와 같은 분산 메시지 브로커와 결합해 Replay, Backfill 과 같은 재처리 시나리오를 완벽하게 지원한다. 이는 시스템 장애 처리나 로직 변경 시에도 데이터 유실 걱정 없이 파이프라인을 복구할 수 있는 근거가 된다.

정리

스트리밍 기반 파이프라인은 소스 데이터베이스와 소비자를 비동기로 분리하고, 변경 이력을 이벤트 단위로 전달하며, 장애 이후에도 재처리가 가능한 흐름을 전제로 한다. 이러한 요구사항을 동시에 만족시키기 위해서는 변경 이력을 append-only 로그로 다루는 구조가 필연적으로 요구된다.

Log-based CDC 방식은 데이터베이스의 트랜잭션 로그를 기반으로 동작함으로써, 추가적인 쿼리나 트리거가 없이도 변경 이력의 완전성, 순서 보장, 재처리 가능성을 자연스럽게 확보한다. 그 결과 Log-based CDC 는 스트리밍 기반 파이프라인의 아키텍처가 요구하는 조건에 가장 잘 부합하는 구현 방식으로 자리잡게 되었다.

📚 요약 / 마무리

  • 실시간 데이터에 대한 요구사항이 증가하면서, 배치 기반 데이터 파이프라인의 한계를 극복하기 위해 CDC(Change Data Capture) 가 중요한 대안으로 부상했다.
  • 구현 방식에 따라 Query-based, Trigger-based, Log-based 로 구분되며, 각 방식은 정확성, 지연 시간, 운영 복잡도 등의 측면에서 명확한 Trade-off 를 가진다.
  • 이 중 Log-based CDC 방식은 트랜잭션 로그를 기반으로 변경 이력을 이벤트 스트림으로 제공함으로써, 스트리밍 기반 데이터 파이프라인의 요구사항을 충족한다.
